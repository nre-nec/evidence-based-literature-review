# Tool Routing and Capability Check | توجيه الأدوات وفحص القدرات

## English

### Three-layer architecture

**Layer A — Research protocol**
Question → Search model → Search → Deduplication → Eligibility → Verification → Appraisal → Extraction → Evidence matrix → Synthesis → Gap analysis → Citation audit → Delivery

**Layer B — Dynamic tool router.** Route by capability, not brand:

| Capability | Preferred tool type |
|---|---|
| Scholarly discovery | Academic evidence/literature search |
| Semantic expansion | Scholarly semantic search |
| Full-text analysis | Publisher/repository/academic full-text tool |
| DOI/metadata verification | DOI registry, publisher, authoritative index |
| Citation networks | Scholarly graph/citation-network service |
| Evidence analysis | Specialized academic evidence tool |
| Standards/guidelines | Issuing organization |
| Document output | Appropriate document-generation capability |

Named services (Consensus, SciSpace, Undermind, Crossref, OpenAlex, PubMed, Semantic Scholar, etc.) are optional examples, not dependencies.

**Layer C — Fallback protocol.** If a preferred tool is unavailable:
1. detect the strongest available scholarly alternative;
2. continue rather than stopping because one connector is missing;
3. use complementary independent sources where useful;
4. reduce claim strength when evidence access is weaker;
5. disclose limitations that materially affect rigor;
6. never silently substitute unsupported model knowledge.

### Step 0 — Capability check
Before asking unnecessary questions:
1. inspect available tools/connectors;
2. identify scholarly search, full-text, DOI/metadata verification, citation-network, and document capabilities;
3. prefer specialized academic tools for scholarly discovery;
4. use general web search mainly for publisher records, official standards, institutional documents, grey literature, and verification;
5. use complementary scholarly sources when this materially improves coverage or reliability;
6. do not narrate routine tool checks unless a limitation affects the deliverable.

### Tool neutrality
Absence of one external service must not block the entire review unless the user's requested task genuinely depends on it. Connector-specific features such as creating a folder are optional enhancements, not prerequisites for rigor.

## العربية

### البنية ثلاثية الطبقات

**أ — البروتوكول البحثي**
السؤال ← نموذج البحث ← الاسترجاع ← إزالة التكرار ← الأهلية ← التحقق ← التقييم النقدي ← الاستخراج ← مصفوفة الأدلة ← التركيب ← الفجوات ← تدقيق الاستشهادات ← التسليم

**ب — موجه الأدوات الديناميكي.** اختر الأداة بحسب القدرة المطلوبة لا اسم المنتج: بحث أكاديمي، بحث دلالي، نص كامل، تحقق DOI، شبكة استشهادات، تحليل أدلة، مصدر رسمي، إنشاء مستند.

**ج — بروتوكول البدائل.** عند غياب الأداة المفضلة:
1. استخدم أقوى بديل أكاديمي متاح.
2. لا توقف المهارة بسبب غياب موصل واحد.
3. استخدم مصادر مستقلة تكاملية عند الحاجة.
4. خفّض قوة الادعاء إذا كانت الأدلة أضعف.
5. اذكر القيود المؤثرة فقط.
6. لا تعوض البحث الأكاديمي بمعرفة غير موثقة.

### الخطوة صفر — فحص القدرات
افحص توفر البحث الأكاديمي، النصوص الكاملة، التحقق من DOI والبيانات، شبكات الاستشهاد، وإنشاء المستندات. أعطِ الأولوية للأدوات الأكاديمية، واستخدم الويب العام أساسًا للناشرين والمعايير والوثائق الرسمية والأدبيات الرمادية والتحقق المكمل.

### الحياد تجاه الأدوات
لا تجعل غياب خدمة أو موصل واحد سببًا لتعطيل المراجعة كلها إلا إذا كان طلب المستخدم يعتمد عليه تحديدًا. إنشاء مجلد داخل منصة، مثلًا، ميزة إضافية وليس شرطًا للصرامة العلمية.
